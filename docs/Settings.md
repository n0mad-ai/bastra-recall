# Settings / Einstellungen

## English

Since 1.2.0 the web UI includes a settings page backed by the local app database. Open the local web UI, choose **Einstellungen**, change the desired fields and choose **Speichern**. The page groups general/language options, search and embeddings, hooks/reflex, code indexing, archiving, tasks, access and updates. The assistant section opens the existing name/address setup; native system changes retain their existing consent flow. Further Jarvis features are outside this change.

Every field comes from the shared definitions used by the CLI. Boolean switches, text/numbers and structured JSON options use the same validators. **Standard** removes the stored override. Environment overrides are displayed and continue to take precedence. A saved value can therefore differ from the effective value. Fields marked as requiring a restart apply when the daemon and affected clients restart. The restart button is available for the managed macOS launchd daemon; other installations use their existing service or process restart procedure.

Tasks are **on by default since 1.2.0**, for new and existing installations. An explicit earlier opt-out is preserved. Enable or disable them in the Tasks section or with `bastra config set tasks.enabled true` / `false`; restart the daemon and connected clients/hooks. An explicit `BASTRA_TASKS` still wins (`1` enables; other values disable). Disable the setting again or set `BASTRA_TASKS=0` and restart to switch them off without cancelling stored tasks. Inside enabled tasks, `tasks.notifications` defaults to true and controls optional macOS notifications immediately; other platforms retain next-contact delivery. It does not enable tasks or mark them read. Local telemetry is controlled by `telemetry.enabled`; `BASTRA_TELEMETRY` (or its legacy `NEXUS_TELEMETRY`) still wins. Both switches use a read-only startup snapshot, so passive imports never create or migrate storage.

The web UI itself (`ui.enabled`) is **on by default on macOS since 1.2.0**, because there it answers only to programs of the macOS account that owns the vault. This applies to new installations and to existing ones without a stored choice. On Linux and other systems this account binding does not exist yet, so the web UI stays off until you switch it on with `bastra map` or `bastra config set ui.enabled true`. Linux has not yet been properly tested in real use; that will follow. On Linux, Recall cannot yet check which user account a local request comes from: every program of every user on the computer reaches the local service. Run it there only on a computer with a single user — not on a shared computer, and not in a container that shares its network with others. Private memories stay hidden from such callers there too. A stored choice always wins: if you switched the web UI off, it stays off; if you switched it on, it stays on. Switch it off with `bastra config set ui.enabled false` (or under General on this page, which you then can no longer reach). It takes effect without a restart.

The Access section masks secrets, edits browser CORS origins and lists OAuth clients for revocation. It never reveals a stored API token. To replace a secret, enter its new value; an untouched blank input keeps the previous value. The existing `bastra token` command remains the separate local token-issuance interface. `daemon.env` is masked as a whole because it can contain sensitive values; provide the complete replacement JSON object when changing it. The implementation applies its allowed pins at startup for service and direct starts as well as forwarder starts. Explicit service environment values take precedence and appear read-only. Forwarder pins retain their existing precedence over the spawning client environment.

Invalid JSON edits keep settings unsaved. Save returns to and focuses the invalid editor; correcting or resetting it permits saving. Restart remains blocked while any unsaved edit exists.

`tasks.chatActiveMinutes` sets the shared genuine-human activity window for Claude Code and attached Codex CLI chats (default 30 minutes, integer 1–1440). Only the chat where you last entered input is selected; an unavailable latest chat never redirects to an older one. Start a task-receiving Codex terminal with `bastra codex`; this changes no Codex settings and requires no additional approval. `tasks.chatConsent` records the one-time **Claude** setup answer and is read-only here. Only an explicit Yes during interactive setup may enable Claude's account-wide incoming messages; No, held/refused or managed receiving settings leave Claude on notification and board delivery without disabling the separately launched Codex bridge. [Chat setup and limits](active-chat-tasks.md#english).

`tasks.reportUndo` sets how long a deleted task report stays in the report list and can be restored: a whole number of minutes, hours or days (`10m`, `6h`, `3d`; 1 minute to 30 days) or `off`, which deletes a report at once (default `10m`). Set it in the Tasks section of Settings or with `bastra config set tasks.reportUndo 1h`; it applies at once, to earlier deletes as well. How many deletes are kept (20) and how many bytes they may take stay fixed. [Task reports](Proactive%20Tasks.md#task-reports).

### Environment controls in the web UI

The Settings page of the web UI exposes the following existing environment options in Models, Recall behaviour, Writing and Logs. The defaults come from the daemon runtime. All twelve store individual pins in the existing `daemon.env` record. Use **Apply**, inspect old/new values in **Changes**, and restart the daemon to apply these pins. **Standard** removes a pin. A real process environment override carries the ENV chip and is read-only. An applied settings pin stays editable even while its replacement or removal awaits restart.

| Key | Environment variable | Default | Input |
|---|---|---|---|
| `embedding.model` | `BASTRA_EMBEDDING_MODEL` | `embeddinggemma` | text |
| `ollama.url` | `BASTRA_OLLAMA_URL` | `http://localhost:11434` | HTTP(S) URL |
| `ollama.keepAlive` | `BASTRA_OLLAMA_KEEP_ALIVE` | `10m` | duration, -1 or 0 |
| `recall.floor` | `BASTRA_RECALL_FLOOR` | `30` | integer 0–100 |
| `prompt.hookMode` | `BASTRA_PROMPT_HOOK_MODE` | `all` | all / retrieval-only |
| `hint.suppress` | `BASTRA_HINT_SUPPRESS` | `shadow` | shadow / off |
| `hint.suppressAfter` | `BASTRA_HINT_SUPPRESS_AFTER` | `8` | integer 0–30 |
| `scope.filterLanes` | `BASTRA_SCOPE_FILTER_LANES` | `shadow` | shadow / enforce |
| `saveNotice` | `BASTRA_SAVE_NOTICE` | `true` | boolean |
| `logs.retention` | `BASTRA_LOG_RETENTION_DAYS` | `90` | 30–365 days |
| `logs.path` | `BASTRA_LOG_PATH` | `~/.bastra/logs (macOS)` | raw path |
| `training.capture` | `BASTRA_TRAINING_CAPTURE` | `false` | boolean |

The log folder default is resolved to the current platform's Bastra data directory. Custom relative paths and literal `~` are passed through as the runtime already does. Retention has a 30-day runtime floor. The hint-suppression options remain shadow/off. Ollama URLs must use HTTP(S) without embedded credentials, query or fragment; keep-alive accepts signed, fractional and compound durations such as `1h30m`.

The same keys work with the CLI, for example `bastra config set hint.suppressAfter 9`. Each command merges only its pin and preserves the others. The advanced masked `daemon.env` JSON editor still replaces the complete object, with validation for changed known pins.

**Start at login** reads the installed service registration, defaulting to off when absent. On macOS the Settings control registers or removes the managed login plist while the current daemon continues running. It takes effect at the next login. Foreign registrations and platforms without this staging adapter are read-only here; the existing `bastra autostart on|off|status` CLI remains available on its supported platforms. The UI saves normal settings first, then login registration. If the second operation fails, successful settings stay saved and the failed login change remains pending.

### Local API

The settings API requires a directly local connection, a loopback Host and an enabled web UI. Forwarded requests are rejected. Create a session with an empty JSON `POST /ui/settings/session`; keep its HttpOnly/SameSite=Strict cookie and the returned CSRF token. `GET /ui/settings` returns registry entries, masked values, effective settings, environment-override information and OAuth client summaries. Send JSON `POST /ui/settings` with `{ "changes": { "docs.language": "de" } }` and the `X-Bastra-Settings-CSRF` header to change settings. A null value removes a stored override; the other stored values of the same group, such as the Claude setup answer `tasks.chatConsent`, stay. Saving one value never stores the defaults of its neighbours. The experiment settings only work together: resetting just one of them is refused, reset all four at once. Invalid patches write nothing. The assistant name is not changed through this route; it uses the dedicated address endpoint `POST /ui/assistant-address` (see below) so its system transaction cannot be bypassed.

`POST /ui/settings/oauth/revoke` accepts a `clientId`; `POST /ui/settings/restart` accepts an empty object when restart is available. Both need the session and CSRF header. Responses and errors never include secret values. Sessions expire after fifteen minutes and are cleared by a daemon restart. Each new session replaces the browser cookie, so an older tab's CSRF token stops matching; such a request returns 403 with `"code": "csrf_mismatch"`, and the web UI then opens a new session once and repeats the request, keeping unsaved changes. The session whose cookie is replaced ends at once, so tabs that keep taking turns never use up the session limit. Origin and Host refusals carry no code and are not repeated.

### Storage and return to the previous version

Settings are stored in namespace `settings` in the local `recall.db`, keyed by the original absolute `cli-settings.json` path. On first adoption the shared adapter automatically backs up the database and retains the original bytes as `cli-settings.json.pre-db`. Repeated reads do not reimport it. The existing typed settings accessors remain supported. See [the local database guide](app-database.md) and [store migration/rollback](app-record-store.md).

To return to the old version, stop all daemon/CLI writers and restore the retained `.pre-db` filename before starting the old binary. To retain newer changes, first use `exportAppRecord("settings", originalAbsolutePath, newDestination)` from the new binary and restore that export instead. Keep the DB, WAL/SHM files and retained originals until the returned version is verified. Never put the database on a sync or network drive. Memories remain Markdown in the vault.

Ein ausdrücklich gesetztes `BASTRA_TASKS` gewinnt weiterhin (`1` schaltet ein; andere Werte schalten aus). Der Schalter aktiviert keine Aufgaben und markiert sie nicht als gelesen. Lokale Telemetrie wird über `telemetry.enabled` gesteuert; `BASTRA_TELEMETRY` beziehungsweise das alte `NEXUS_TELEMETRY` gewinnt weiter. Beide Schalter verwenden einen nur lesenden Start-Schnappschuss; passive Modulimporte legen keinen Speicher an und migrieren nichts.

Die Weboberfläche selbst (`ui.enabled`) ist **unter macOS seit 1.2.0 standardmäßig an**, weil sie dort nur Programmen des macOS-Kontos antwortet, dem der Vault gehört. Das gilt für neue Installationen und für bestehende ohne gespeicherte Wahl. Unter Linux und anderen Systemen gibt es diese Kontobindung noch nicht; dort bleibt die Weboberfläche aus, bis du sie mit `bastra map` oder `bastra config set ui.enabled true` einschaltest. Linux ist im echten Einsatz noch nicht richtig getestet; das wird nachgeholt. Betreibe Recall dort nur auf einem Rechner mit einem einzigen Benutzer – nicht auf einem gemeinsam genutzten Rechner und nicht in einem Container, der sein Netzwerk mit anderen teilt. Private Memories bleiben auch dort für solche Aufrufer verborgen. Eine gespeicherte Wahl gilt immer: Wer die Weboberfläche ausgeschaltet hat, behält das; wer sie eingeschaltet hat, ebenso. Ausschalten mit `bastra config set ui.enabled false` (oder unter Allgemein auf dieser Seite, die du danach nicht mehr erreichst). Es wirkt ohne Neustart.

Der Zugangsbereich maskiert Geheimnisse, bearbeitet erlaubte Browser-CORS-Ursprünge und listet OAuth-Clients zum Widerrufen. Ein gespeichertes API-Token wird nie angezeigt. Zum Ersetzen ein neues Geheimnis eingeben; ein unverändert leeres Eingabefeld behält den bisherigen Wert. `bastra token` bleibt die gesonderte lokale Oberfläche zum Ausstellen von Tokens. `daemon.env` wird vollständig maskiert, weil es sensible Werte enthalten kann; beim Ändern das vollständige neue JSON-Objekt angeben. Die Implementierung liest erlaubte Vorgaben beim Start auch für Dienste und direkte Starts ein. Ausdrückliche Umgebungswerte des Dienstes haben Vorrang und erscheinen schreibgeschützt. Vorgaben für den Forwarder behalten ihren bisherigen Vorrang vor der Umgebung des startenden Clients.

Ungültige JSON-Änderungen bleiben ungespeichert. Speichern führt zum fehlerhaften Feld und fokussiert es; Korrigieren oder Zurücksetzen erlaubt das Speichern. Bei ungespeicherten Änderungen bleibt der Neustart gesperrt.

`tasks.chatActiveMinutes` setzt die gemeinsame Aktivitätsgrenze seit der letzten echten Nutzernachricht für Claude Code und angebundene Codex-CLI-Chats (Standard 30 Minuten, ganze Zahl 1–1440). Gewählt wird nur der Chat mit deiner letzten Eingabe; ist er nicht erreichbar, wird nie auf einen älteren ausgewichen. Starte ein Codex-Terminal für Aufgabenmeldungen mit `bastra codex`; dabei ändern sich keine Codex-Einstellungen und eine zusätzliche Freigabe entfällt. `tasks.chatConsent` hält die einmalige **Claude**-Einrichtungsantwort fest und ist hier nur lesbar. Nur ein ausdrückliches Ja in der interaktiven Einrichtung darf Claude Codes kontoweiten Nachrichteneingang aktivieren; bei Nein, gehaltenem/abgewiesenem oder verwaltetem Empfang bleibt Claude bei Mitteilung und Brett, ohne die gesondert gestartete Codex-Verbindung abzuschalten. [Chat-Einrichtung und Grenzen](active-chat-tasks.md#deutsch).

`tasks.reportUndo` legt fest, wie lange ein gelöschter Aufgabenbericht in der Berichtsliste bleibt und sich wiederherstellen lässt: eine ganze Zahl Minuten, Stunden oder Tage (`10m`, `6h`, `3d`; 1 Minute bis 30 Tage) oder `off`, dann ist ein gelöschter Bericht sofort weg (Standard `10m`). Einstellbar im Aufgabenbereich der Einstellungen oder mit `bastra config set tasks.reportUndo 1h`; gilt sofort, auch für frühere Löschungen. Wie viele Löschungen gehalten werden (20) und wie viele Bytes sie belegen dürfen, bleibt fest. [Aufgabenberichte](Proaktive%20Aufgaben.md#aufgabenberichte).

Die Einstellungsseite der Weboberfläche zeigt die folgenden vorhandenen Umgebungsoptionen in Modelle, Abrufverhalten, Schreiben und Protokolle. Die Standards stammen aus dem Daemon. Alle zwölf speichern einzelne Vorgaben im bestehenden `daemon.env`-Datensatz. Mit **Übernehmen** speichern, alte/neue Werte im Reiter **Änderungen** prüfen und den Daemon zum Anwenden neu starten. **Standard** entfernt eine Vorgabe. Eine echte Prozess-Umgebungsvariable trägt den ENV-Chip und ist schreibgeschützt. Eine beim Start angewendete gespeicherte Vorgabe bleibt bearbeitbar, auch wenn ihre Ersetzung oder Entfernung noch auf den Neustart wartet.

Der Standardordner für Protokolle wird zum Bastra-Datenverzeichnis der jeweiligen Plattform aufgelöst. Eigene relative Pfade und ein wörtliches `~` werden wie bisher unverändert an die Laufzeit weitergegeben. Die Aufbewahrung hat eine Untergrenze von 30 Tagen. Die Hinweisunterdrückung bleibt bei shadow/off. Ollama-URLs verwenden HTTP(S) ohne eingebettete Zugangsdaten, Query oder Fragment. Keep-alive erlaubt vorzeichenbehaftete, gebrochene und zusammengesetzte Dauern wie `1h30m`.

Dieselben Schlüssel funktionieren über die CLI, etwa `bastra config set hint.suppressAfter 9`. Jeder Befehl ändert nur seine Vorgabe und erhält die übrigen. Der maskierte erweiterte JSON-Editor für `daemon.env` ersetzt weiterhin das gesamte Objekt und validiert geänderte bekannte Vorgaben.

**Bei Anmeldung starten** liest die installierte Dienstregistrierung und ist ohne Registrierung standardmäßig aus. Unter macOS legt der Settings-Schalter den verwalteten Login-Plist an oder entfernt ihn, während der aktuelle Daemon weiterläuft. Die Änderung gilt bei der nächsten Anmeldung. Fremde Registrierungen und Plattformen ohne diesen Adapter sind hier schreibgeschützt. Die bestehende CLI `bastra autostart on|off|status` bleibt auf ihren unterstützten Plattformen verfügbar. Die UI speichert normale Einstellungen zuerst, danach die Login-Registrierung. Scheitert die zweite Operation, bleiben die erfolgreichen Einstellungen gespeichert und die fehlgeschlagene Login-Änderung bleibt offen.

### Lokale API

Die Einstellungs-API verlangt eine direkte lokale Verbindung, einen Loopback-Host und eine eingeschaltete Web-UI. Weitergeleitete Anfragen werden abgewiesen. Eine leere JSON-Anfrage an `POST /ui/settings/session` legt die Sitzung an; das HttpOnly-/SameSite=Strict-Cookie und den zurückgegebenen CSRF-Token aufbewahren. `GET /ui/settings` liefert Registereinträge, maskierte Werte, wirksame Einstellungen, Umgebungsüberschreibungen und OAuth-Client-Zusammenfassungen. Änderungen als JSON an `POST /ui/settings` senden, etwa `{ "changes": { "docs.language": "de" } }`, mit dem Header `X-Bastra-Settings-CSRF`. Null entfernt eine gespeicherte Vorgabe; die übrigen gespeicherten Werte derselben Gruppe, etwa die Claude-Einrichtungsantwort `tasks.chatConsent`, bleiben erhalten. Das Speichern eines Werts speichert nie die Standards seiner Nachbarn mit. Die Experiment-Einstellungen wirken nur gemeinsam: Nur eine davon zurückzusetzen wird abgelehnt, alle vier zusammen zurücksetzen. Ungültige Änderungen schreiben nichts. Der Assistentenname wird nicht über diese Route geändert, sondern über den eigenen Adress-Endpunkt `POST /ui/assistant-address` (siehe unten), damit dessen Systemtransaktion nicht umgangen werden kann.

`POST /ui/settings/oauth/revoke` erwartet `clientId`; `POST /ui/settings/restart` ein leeres Objekt, sofern Neustart verfügbar ist. Beide verlangen Sitzung und CSRF-Header. Antworten und Fehler enthalten keine Geheimnisse. Sitzungen laufen nach fünfzehn Minuten ab und werden beim Daemon-Neustart verworfen. Jede neue Sitzung ersetzt das Browser-Cookie, der CSRF-Token eines älteren Tabs passt dann nicht mehr; eine solche Anfrage liefert 403 mit `"code": "csrf_mismatch"`. Die Weboberfläche öffnet dann einmal eine neue Sitzung und wiederholt die Anfrage; nicht übernommene Änderungen bleiben erhalten. Die Sitzung, deren Cookie ersetzt wird, endet sofort; abwechselnd speichernde Tabs schöpfen die Sitzungsgrenze daher nicht aus. Abweisungen wegen Origin oder Host tragen keinen Code und werden nicht wiederholt.

### Speicherung und Rückkehr zur vorherigen Version

Die Einstellungen liegen im Namespace `settings` der lokalen `recall.db`; Schlüssel ist der ursprüngliche absolute Pfad von `cli-settings.json`. Beim ersten Umzug sichert der gemeinsame Adapter automatisch die Datenbank und erhält die Originalbytes als `cli-settings.json.pre-db`. Wiederholtes Lesen importiert diese Datei nicht erneut. Die bisherigen typisierten Einstellungszugriffe bleiben erhalten. Siehe [lokale Datenbank](app-database.md) und [Speicherumzug/Rückweg](app-record-store.md).

Für die Rückkehr zuerst alle Daemon-/CLI-Schreiber stoppen und die erhaltene `.pre-db`-Datei unter ihrem alten Namen wiederherstellen, dann die alte Version starten. Sollen neuere Änderungen erhalten bleiben, zuvor mit der neuen Version `exportAppRecord("settings", ursprünglicherAbsoluterPfad, neuesZiel)` ausführen und stattdessen diesen Export wiederherstellen. DB, WAL-/SHM-Dateien und Originale bis zur Prüfung der zurückgekehrten Version bewahren. Die Datenbank gehört nie auf ein Sync- oder Netzlaufwerk. Erinnerungen bleiben Markdown im Vault.


## Agent and personality

The free Settings page of the web UI has an **Agent and personality** group. Its first field is the assistant's name. The name is shown everywhere exactly as typed (`Jarvis`, `Jürgen`, `Mein Jarvis`, any language and script; stored as `assistant.displayName`). Only technical limits apply: 1–64 characters (code points), trimmed and Unicode-normalized (NFC), no control characters or line breaks; only such input is rejected. The local address (`assistant.name`) is derived language-independently: runs of characters other than letters, marks and digits become one hyphen, then IDNA/UTS #46 lower-cases and encodes the name (`Jarvis` → `jarvis`, `Mein Jarvis` → `mein-jarvis`, `Jürgen` → `xn--jrgen-kva`, typed as `http://jürgen/`). hosts, the port-80 helper and the gateway only ever see this ASCII label. If no address can be derived (only emoji, a reserved name, more than 63 characters in address form), the name is saved anyway, the existing address (or none) stays and the row says so. The row shows the readable address and adds the `xn--` form when it differs. The gateway accepts the `xn--` Host that browsers and Node send and the UTF-8 form of clients without IDN support (such as macOS curl); whether a browser opens a bare non-ASCII name instead of searching is up to the browser. Apply sends `{ "name": "Jarvis", "systemConsent": true }` to `POST /ui/assistant-address`: saving is the instruction. On macOS, a derived address that is not yet registered is then set up with the existing address transaction; macOS asks once for an administrator password. A change that derives the same address (`jarvis` → `Jarvis`) leaves a registered address untouched. If the address step fails or is cancelled, the name still applies, the previous address stays in place and the row says that `http://<name>/` still needs setting up; **Set up address** repeats the step. On other systems an administrator sets up the short name. Settings saved before the display name existed keep showing the stored address name (in readable form) until the name is entered again.

The group also holds the base personality. Choose Balanced (default), Direct, Warm, Playful or Sparring partner; the short explanation changes with the selection. Describe in your own words how you want to be treated; the field grows with your text, and there is no short limit (a protective limit of 8,000 characters applies, and a counter appears when you get close to it). Apply saves both values through the ordinary settings workflow; Discard removes unsaved edits. No daemon restart is needed.

The values are `soul.direction` (`balanced`, `direct`, `warm`, `playful`, `sparring`) and `soul.text` (default empty). Returning a value to its default clears that override. They shape tone, length, humor and directness in the agent window and in the session context of connected assistants. Start a new hook session to receive changed preferences. Hookless clients receive the block once at the first tool call of their MCP-forwarder process; if that process is reused, reconnect or restart the client. No mid-session update contract is added. Balanced with no text adds no client context. Preferences do not alter facts, task data, navigation intent, permissions or binding rules. Free text is quoted style data; instructions to override those boundaries are not granted authority.

Since 1.2.0 this is the base personality only. It does not learn from interactions or store episodes; those follow in v1.3.0 (#1504). It uses the existing local settings store, with no database schema change.

## Agent und Persoenlichkeit

Die freie Einstellungsseite der Weboberfläche enthält die Gruppe **Agent und Persönlichkeit**. Ihr erstes Feld ist der Name des Assistenten. Der Name erscheint überall genau so, wie er eingegeben wurde (`Jarvis`, `Jürgen`, `Mein Jarvis`, in jeder Sprache und Schrift; gespeichert als `assistant.displayName`). Es gelten nur technische Grenzen: 1–64 Zeichen (Codepoints), getrimmt und Unicode-normalisiert (NFC), keine Steuerzeichen oder Zeilenumbrüche; nur solche Eingaben werden abgelehnt. Die lokale Adresse (`assistant.name`) wird sprachunabhängig abgeleitet: Folgen von Zeichen außer Buchstaben, Zeichen-Ergänzungen und Ziffern werden zu einem Bindestrich, danach schreibt IDNA/UTS #46 den Namen klein und kodiert ihn (`Jarvis` → `jarvis`, `Mein Jarvis` → `mein-jarvis`, `Jürgen` → `xn--jrgen-kva`, eingetippt als `http://jürgen/`). hosts, Port-80-Helfer und Gateway sehen ausschließlich dieses ASCII-Label. Lässt sich keine Adresse ableiten (nur Emoji, reservierter Name, mehr als 63 Zeichen in Adressform), wird der Name trotzdem gespeichert, die bisherige Adresse (oder keine) bleibt, und die Zeile sagt das. Die Zeile zeigt die lesbare Adresse und ergänzt die `xn--`-Form, wenn sie abweicht. Das Gateway nimmt den `xn--`-Host an, den Browser und Node senden, und die UTF-8-Form von Programmen ohne IDN-Unterstützung (etwa curl unter macOS); ob ein Browser einen puren Namen mit Sonderzeichen öffnet statt zu suchen, entscheidet der Browser. Übernehmen sendet `{ "name": "Jarvis", "systemConsent": true }` an `POST /ui/assistant-address`: Das Speichern ist die Anweisung. Unter macOS wird eine abgeleitete Adresse, die noch nicht eingetragen ist, danach über die vorhandene Adress-Transaktion eingerichtet; macOS fragt dabei einmal nach dem Administratorpasswort. Ergibt der neue Name dieselbe Adresse (`jarvis` → `Jarvis`), bleibt eine eingetragene Adresse unberührt. Scheitert der Adressschritt oder wird er abgebrochen, gilt der Name trotzdem, die bisherige Adresse bleibt bestehen und die Zeile zeigt, dass `http://<name>/` noch eingerichtet werden muss; **Adresse einrichten** wiederholt den Schritt. Auf anderen Systemen richtet der Administrator den Kurznamen ein. Einstellungen aus der Zeit vor dem Anzeigenamen zeigen weiter den gespeicherten Adressnamen (in lesbarer Form), bis der Name neu eingegeben wird.

Zur Gruppe gehört außerdem die Grundpersönlichkeit. Wähle Ausgewogen (Standard), Direkt, Warm, Locker oder Sparringspartner; die kurze Erklärung passt sich der Auswahl an. Beschreibe in eigenen Worten, wie du behandelt werden möchtest; das Feld wächst mit dem Text und kennt keine knappe Grenze (als Schutz gelten 8.000 Zeichen, ein Zähler erscheint erst kurz davor). Übernehmen speichert beide Werte im normalen Einstellungsablauf; Verwerfen entfernt ungespeicherte Änderungen. Ein Daemon-Neustart ist nicht nötig.

Die Werte heißen `soul.direction` (`balanced`, `direct`, `warm`, `playful`, `sparring`) und `soul.text` (Standard leer). Zurück zum Standard entfernt die jeweilige Überschreibung. Sie gestalten Ton, Länge, Humor und Direktheit im Agentenfenster und im Sitzungskontext angebundener Assistenten. Für geänderte Wünsche eine neue Hook-Sitzung starten. Hooklose Clients erhalten den Block einmal beim ersten Toolaufruf ihres MCP-Forwarder-Prozesses; bleibt dieser Prozess bestehen, den Client neu verbinden oder neu starten. Eine Aktualisierung mitten in laufenden Sitzungen ist hier nicht ergänzt. Ausgewogen ohne Freitext ergänzt keinen Client-Kontext. Wünsche ändern weder Fakten, Aufgabendaten, Navigationsabsicht, Rechte noch verbindliche Regeln. Freitext wird als zitierter Stilwunsch eingebettet; Anweisungen zum Aufheben dieser Grenzen erhalten dadurch keine Geltung.

Seit 1.2.0 gibt es nur die Grundpersönlichkeit. Sie lernt nicht aus Interaktionen und speichert keine Episoden; das folgt in v1.3.0 (#1504). Sie nutzt die bestehenden lokalen Einstellungen ohne Änderung am Datenbankschema.
