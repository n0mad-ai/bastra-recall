# Measured context load (#1371), 2026-11-03

Checked in for #1465. This is the English version of the measurement report written on 2026-11-03 for #1371 (originally a German handover file in the repository root, never committed). The numbers are unchanged. Sections "Provenance" and "Repeating the measurement" were added on 2026-11-17.

**Summary.** The suspicion holds for the added rule and check texts: measured hook text grows from about 539 to 851 estimated tokens per delivered prompt-hook round (+58 %), while the total measured Bastra text per session stays almost the same. The three largest new recurring surfaces are the rule kernel, the rulebook/correspondence notices and the results of `rulebook_check`. The extra load comes from several complementary delivery paths and enforced check steps; a general flooding of the context by constantly repeated full conventions is not confirmed by this measurement.

Measured and reported only: no product code, commit, PR or issue comment. Rule delivery stays mandatory; no word lists or wording detection against user text are proposed.

## How to read the numbers

Tokens are **characters / 4**, not an exact model tokenization. "Per round" in the main table means per **non-empty Bastra prompt hook**: 20 before, 16 after. Agent messages can also trigger such hooks; there were only 24 resp. 6 human prompts. Normalising to human prompts alone would strongly overstate the new load. Startup, tool and stop texts are spread over these rounds for this comparison; they do not actually occur on every prompt.

Two working sessions from the v1.1.1 period (Oct 20–21) are compared with two sessions **after the v1.1.8 release time** (Oct 31 – Nov 3). Different tasks and session lengths: not a controlled before/after experiment. Date and git tags establish the periods, not the daemon version installed for each historical event. The running case of Nov 3 is the confirmed v1.1.8 example. The RC session on the morning of Oct 31 is excluded from the main table.

**Cross-check:** the total is 209,115 against 209,482 characters, only +0.18 % over two sessions each. The increase per hook round is about 25 % because the later sample has fewer rounds. A general claim "v1.1.8 fills every session more" is therefore not supported. Hook text itself grows by 26 % per session; tool answers are smaller in the later sample. The largest absolute result surfaces after the release remain `load_memory` (23,970 tokens in total), `recall` (6,375) and the rule kernel (4,663). Loading full memories is larger than the new control confirmations.

`list_rules` was observed once in the excluded RC section with 25,789 characters / 6,447 tokens. After the release cut no further call occurred in the sample; that does not mean the catalog is free. Its output can contain index information delivered earlier.

### Start, re-delivery and compaction

In the controlled live case SessionStart delivers **9,689 characters / 2,422 tokens**, of which 9,272 / 2,318 are the rule kernel. The rest is the language notice and the note about deferred sections. The kernel contains one full Always text and a paged index, not all 74 rule texts. The two kernels counted after the release are one after compaction in `89a72802` and the startup kernel in `422c7ab9`. Whole identical lines give 0 % repetition in the counted context there; after a context reset re-delivery can be necessary.

Source limits: kernel at most 9,400 characters / 2,350 tokens, total SessionStart addition below 10,000 characters; Always part at most 8,000 characters inside the shared kernel budget. After 25 tool calls without a prompt the kernel can be delivered again. This measurement run itself received such re-deliveries. There is no measured universal average for long sessions or all compactions.

### Conventions are not repeated in full everywhere

In the live control the first two `rulebook_check` answers are **1,152 and 1,054 characters**. Their `conventions` contain **IDs and revisions, no bodies**. Serialized separately, these fields are 525 and 476 characters; they are part of the answer and must not be added to the answer total again. For a check without an explicit `task` the field is absent in the current code.

An `<active-conventions>` block was not found in the live API excerpt, but six times after the release in the other session. The renderer repeats it deliberately per round and bypasses the normal hint deduplication. Controlled example: one validator rule costs about 128–131 tokens per block, six similarly long entries about 305–320. The measured blocks are state/check notices, not repeated full memory bodies.

## Tool descriptions: a separate cost block

This block is **not** included in the session totals above. Counted are native description strings, without input schemas and calls. The release comparison is computed exactly against the git states.

Without tasks the native full catalog grows by **1,199 tokens / 27.1 %**. Largest current single descriptions: `save_memory` 6,028 characters, `rulebook_check` 2,820, `recall` 2,556. `load_memory` grows from 445 to 725 characters, `validate_artifact` is new with 938. `rulebook_check` alone costs 705 tokens per actually loaded definition.

**Claude:** in the actual API tool selection of the live session only four Bastra descriptions are loaded after ToolSearch: list_rules 483, load_memory 727, recall 2,556 and rulebook_check 2,820 characters, together **6,586 characters / 1,647 tokens**. The small difference to the source load_memory is a rendering/counting difference. Separately there is an MCP server instruction of 2,412 characters in the startup API blob. Unloaded tools must not be counted for Claude as a fully loaded simultaneous catalog.

**Codex:** the 44 tool metadata entries visible here each repeat **2,393 characters** of general server/code-awareness instructions: together **105,292 characters / 26,323 tokens** for these 44 copies alone. All projected description texts together have 155,965 characters / 38,991 tokens, including appended tool declarations. That is a conspicuously large **metadata potential**, not proof that all definitions sit in the active model context at the same time. This addition was already the same length in the native server instructions of both releases, so it is not a proven v1.1.8 increase. Delivering it centrally instead of 44 copies would arithmetically avoid up to 25,725 tokens, provided the runtime actually loads them all. Claude does not show this 44-fold repetition in the examined API shape.

## Benefit and additional work steps

After the release **eight denial events** were counted: six before tool calls and two at stop. Before, no corresponding Bastra check denial was observed. Seven of the eight have a follow-up action in the frozen material; in six of them `rulebook_check` or `load_memory` follows within the next three assistant messages. That is an observable behaviour change after a notice, not proven semantic rule compliance. The last stop denial had no follow-up yet when the measurement ended.

Concrete continuations: `89a72802`, Oct 31, 22:06:52 UTC: Bash denied → load_memory → Bash; 22:26:53 UTC: Bash denied → rulebook_check → Bash. In `422c7ab9` the first Bash call `toolu_019bcetDLq64BDN2q6ovftwe` is denied, followed by four loads, one check and the Bash retry. Additional control calls and retries are therefore real. Not every single load would have been skipped without the denial, and several calls can be bundled in one model answer: **eight events are not a reliable count of eight extra API rounds**. An exact causal number of extra model rounds cannot be determined from this material.

A Write call is also denied with a rulebook obligation after the release. For exactly the GitHub must-loads from #1372 this sample gives no separately reliable rate or size distribution; the general denial surface is measured, an isolated proof of each GitHub variant would be invented. The measured tool interruptions after the release reach up to 1,403 characters, the current live Bash notice has 244 characters. Stop repairs have 457 characters / 114 tokens per event in the real examples. A controlled renderer case gives 329–331 characters for context plus system message depending on the error; that is an example, not a replacement for the session measurement.

The later delegation and loading of language/milestone rules fit the delivered rules. Delegation had already been requested by the user, though, so no causal "benefit rate" can be derived. More text does not automatically mean more rule compliance. A semantic effect of the rule kernel or the draft hints cannot be established here.

## Five possible reductions — not decided

| Idea | Arithmetic saving | How rule delivery would have to be preserved |
|---|---|---|
| Deliver the general Codex server instruction once, centrally | at most 25,725 tokens with 44 definitions actually loaded at once; consider Claude separately | The full central instruction must be available before tool use and come again after a context reset; check the runtime first. |
| Replace unchanged long prompt procedure notices with a short reminder | target e.g. 200 instead of an average 829 characters: about 157 tokens per notice; about 2,518 tokens over the 16 measured notices | First delivery, rule change and reset deliver the full procedure; current round obligations and exceptions stay. The rule decision is never skipped. |
| Condense the rulebook_check description to about 800 characters with reliably loadable details | about 505 tokens per loaded definition | Required fields, validity, action load obligations and correspondence exceptions stay fully available before the affected use. |
| Briefly confirm unchanged active-conventions states | example 131 → 40 tokens: about 91 per truly unchanged block | IDs, revisions and validator binding stay; full re-delivery on change or reset. The six measured blocks are not all identical, so no flat extrapolation. |
| Load unused tools only on demand | with tasks at most about 2,131 tokens for the 30 task descriptions alone, if they are actually loaded today | Discoverability and full description before use preserved. In the Claude control loading is already on demand; no corresponding extra gain shown there. |

The savings are target calculations, not tested changes, and must not simply be added: central boilerplate and on-demand loading overlap. On this data the rule kernel itself would not be the first thing to shorten: it delivers the rules and their index within an existing budget. The recurring procedure notices show more directly proven repetition. A budget check commissioned later should measure the actually delivered text surfaces per context and round and check delivery on change/reset; no check was built here.

## Repeating the measurement

The transcript-based split above cannot be rerun without the lost scripts. What every hook lane books about itself in the event log can be rerun at any time, read-only:

```sh
SINCE=2026-11-03 UNTIL=2026-11-16 npm run hook-context-load --workspace @bastra-recall/eval
```

`packages/eval/src/hook-context-load.ts` reports per lane event kind and agent (main thread / subagent) the calls, the calls that injected text and the injected size (`hint_tokens_est`), draft hints per hook event, the gate lane's rule-kernel re-deliveries (full text, identical repeats within a session, short reminders) and the plan lane with its follow-through. It is the before/after instrument for #1460, #1461 and #1464; their baselines are recorded in `hook-context-load-2026-11-17.md`.
